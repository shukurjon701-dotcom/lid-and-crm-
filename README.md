# LID CRM — система управления учебным центром

Дашборды для одного филиала: обзор руководителя, администратор, call-центр и финансы.
Сайт запущен на **http://localhost:3000**.

## Вход

| Логин | Пароль | Роль |
|---|---|---|
| `admin1` | `admin1-2026` | Администратор — полный доступ |
| `admin2` | `admin2-2026` | Администратор — полный доступ |
| `admin3` | `admin3-2026` | Администратор — полный доступ |

Администратор видит и может всё: все четыре дашборда, лиды, учеников, группы,
платежи, расходы, должников, сотрудников и журнал изменений.

Сменить пароль:

```bash
node -e "console.log(require('bcryptjs').hashSync('новый-пароль',10))"
# вставить хеш в src/server/auth/accounts.ts (и в prisma/seed.ts, если работаете с БД)
```

## Запуск

```bash
npm run dev          # http://localhost:3000
```

Node.js установлен локально в `~/.local/opt/node` (v24 LTS) и подключён через `~/.local/bin`.

## Данные: только настоящие

Приложение считает метрики из одного типа `Dataset` (`src/server/data/types.ts`),
и единственный его источник — Postgres.

Подставного набора нет. Если база недоступна или её схема устарела, приложение
показывает экран «Данные недоступны» (`src/app/error.tsx`) с причиной, а не
работающий на вид дашборд. Так сделано намеренно: выдуманные цифры неотличимы
от настоящих, по ним принимают решения, и подмена вскрывается через неделю.

Ученики, лиды, звонки и платежи попадают в базу только из настоящих источников —
Sahab, Bitrix24 и АТС onlinePBX (см. «Синхронизация»).

### Управление базой

```bash
docker compose up -d db     # запустить Postgres (уже настроен, том сохраняется)
docker compose stop db      # остановить
npm run db:push             # применить схему
npm run db:seed             # филиал + admin1/2/3 + статьи расходов (ничего не стирает)
npm run db:studio           # смотреть и править таблицы в браузере
```

`prisma/seed.ts` — только первичная настройка: филиал, три администратора
`admin1/2/3` с теми же паролями, что и в `src/server/auth/accounts.ts`, и
справочник статей расходов. Учеников и платежи он не создаёт: раньше создавал,
и база наполнялась случайными записями.

### Почему переходы между разделами быстрые

Каждый раздел собирается на сервере и читает весь набор данных филиала —
это десять запросов по всем таблицам. Чтобы не повторять их на каждый клик,
снимок базы живёт **20 секунд** (`DATASET_TTL_MS` в `src/server/data/source.ts`),
и параллельные запросы ждут один общий снимок, а не отправляют свои. Данные
всё равно меняются только в момент синхронизации, а она сбрасывает снимок
сама (`invalidateDataset` вызывается из `/api/refresh`), поэтому кнопка
«Обновить» показывает свежие числа сразу.

Снимок живёт в памяти процесса. Если однажды приложение поднимут в нескольких
экземплярах, у каждого будет свой — на глаз это не заметно (данные разъезжаются
максимум на те же 20 секунд), но помнить стоит.

Второе — `src/app/(dashboard)/loading.tsx`: скелет раздела. Без него браузер
держит старый экран, пока сервер не ответит, и клик по меню выглядит как
зависание. Со скелетом каркас появляется мгновенно, и Next заранее подтягивает
его при наведении на пункт меню.

Локально мерить скорость по `npm run dev` бессмысленно: dev-сервер компилирует
раздел при первом заходе. Смотреть надо прод-сборку — `npm run build && npm run start`.
И не запускать сборку, пока рядом работает `npm run dev`: они пишут в один
и тот же каталог `.next`, после чего dev-сервер начинает перекомпилировать всё
подряд и отвечает секундами вместо миллисекунд (лечится перезапуском).

## Откуда берутся данные

| Источник | Что даёт | Команда |
|---|---|---|
| **Sahab** | ученики, группы, платежи, расходы, заморозки, посещаемость | `npm run sync:sahab` |
| **Bitrix24** | лиды, визиты, сотрудники | `npm run sync:bitrix` |
| **onlinePBX** | звонки и показатели операторов call-центра | `npm run sync:pbx` |
| **Таблица книг** | склад книг: остатки, цены, закупки и продажи | `npm run import:books` |

Каждая синхронизация трогает только свою область: Sahab не стирает лидов Bitrix,
Bitrix не стирает учеников Sahab, книги живут в своём разделе и в расходы центра
не попадают.

## Bitrix24 — call-центр

```bash
npm run sync:bitrix -- --dry-run     # показать, что придёт
npm run sync:bitrix                  # перенести (по умолчанию 90 дней)
npm run sync:bitrix -- --days=180    # больше истории
```

Доступ — входящий вебхук (`BITRIX_WEBHOOK` в `.env`), права `crm`, `telephony`, `user`.

Разметка статусов вашего портала зашита в `scripts/import/bitrix-sync.ts`:
«Sifatsiz lead» и «Bekor bo'ldi» считаются нецелевыми, остальные — целевые лиды;
«Sinov darsiga yozilganlar» и «Keldi/Kirdi» превращаются в визиты. Если статусы
на портале поменяются, поправить нужно только таблицу `STATUS_MAP`.

Звонки Bitrix больше не импортируются: телефония живёт в onlinePBX (ниже).

## onlinePBX — звонки операторов

```bash
npm run sync:pbx -- --users       # внутренние номера и кто за ними закреплён
npm run sync:pbx -- --dry-run     # показатели по дням, ничего не записывая
npm run sync:pbx                  # перенести звонки (по умолчанию 7 суток)
npm run sync:pbx -- --days=30     # больше истории
```

Доступ — `PBX_DOMAIN` и `PBX_API_KEY` в `.env`. Ключ берётся в панели onlinePBX
(Интеграция → API), домен выглядит как `pbx36133.onpbx.ru`.

Звонок ложится на оператора по внутреннему номеру (`User.pbxExtension`). При
первой синхронизации номера привязываются к сотрудникам по имени из АТС, а если
такого сотрудника в CRM нет — он заводится с логином `pbx-101`. Дальше связь
живёт в базе, и переименование в АТС её не ломает.

Входящий звонок звонит сразу нескольким операторам — засчитывается тому, кто снял
трубку. Колонка «В разговоре» — чистое время разговора (`user_talk_time`), без
ожидания ответа. Разговор дольше 5 минут считается консультацией-уроком
(Call dars). Звонки, не дошедшие ни до одного внутреннего номера, в статистику
call-центра не попадают.

Кнопка «Обновить» в шапке тянет последние трое суток; повторная выгрузка того же
периода не задваивает историю — звонок узнаётся по `uuid` из АТС.

## Книги

```bash
npm run import:books -- --dry-run     # показать склад, ничего не записывая
npm run import:books                  # перенести склад, закупки и продажи
```

Книги — отдельный раздел «Книги» (`/books`), а не статья расходов: у учебника
есть остаток на складе, закупочная цена и цена продажи. Лист `OMBOR` даёт
остатки и цены, `BUYURTMA` — закупки у поставщика, `SOTUV` — продажи ученикам,
`KITOB MOLIYASI` не переносится (сводка по дням считается сама).

Импорт заодно убирает прежние книжные записи из финансов: расходы статьи
«Kitoblar (книги)» и платежи с комментарием «Kitob sotuvi».

## CRM Sahab — ученики и деньги

```bash
npm run sync:sahab -- --dry-run   # показать, что придёт, ничего не записывая
npm run sync:sahab                # перенести в базу
```

Учётные данные служебного аккаунта — в `.env` (`SAHAB_PHONE`, `SAHAB_PASSWORD`).

Две особенности их API, без которых ничего не работает:

* вход — `POST /accounts/login/` (а `/auth/login` это маршрут интерфейса);
* каждый запрос обязан нести заголовок `x-tenant-domain: arabicacademy.sahab.uz` —
  Sahab обслуживает много центров на одном API, без заголовка всё отвечает 404.
* после входа нужно выбрать профиль (`/accounts/set-profile-type/`) и филиал
  (`/accounts/set-current-branch/`), иначе часть разделов закрыта.

Что откуда берётся:

| Источник | Данные |
|---|---|
| **Sahab** | ученики, группы, курсы, платежи, расходы, заморозки, посещаемость |
| **Google-таблица** | лиды и пробные уроки — в Sahab их нет |

Поэтому `sync:sahab` переписывает учеников, группы и деньги, но **не трогает лидов**,
загруженных из таблицы.

Ученик считается активным, только если занимается в действующей группе. В Sahab
1251 карточка, но у 878 нет ни одной группы — это архив; они переносятся со статусом
«ушёл» без даты ухода, чтобы не искажать отток и при этом находиться поиском.

## Рабочая таблица центра (Google Sheets)

Таблица подключена напрямую — выгружать ничего не нужно:

```bash
npm run import:sheets -- --dry-run    # разобрать и показать, в базу не писать
npm run import:sheets -- --replace    # перезалить: стереть прежнее и загрузить заново
```

Ссылка берётся из `GOOGLE_SHEET_ID` в `.env`. Таблица должна быть открыта по ссылке.

Как это работает:

* **Статус берётся из цвета строки** — по легенде с листа «Ranglar»: зелёный = оплатил,
  жёлтый = учится, но не оплатил (это должник), белый = пробный урок, красный = не пришёл,
  синий = Evro guruh, фиолетовый = должен прийти. CSV цвета теряет, поэтому книга
  скачивается в формате `.xlsx` и читается вместе со стилями (`scripts/import/xlsx.ts`).
* **Колонки определяются по содержимому**, а не по букве: в разных месяцах структура
  отличается (в `offaprel` всё сдвинуто на колонку влево, у `Offline Nayabr` свой порядок).
  Опора — колонка с телефонами, имя всегда слева от неё, группа справа
  (`scripts/import/layout.ts`).
* **Один человек = одна запись**, даже если он встречается в нескольких месяцах:
  склейка по телефону, статус берётся из последнего месяца, оплаты суммируются.
* Зелёный/жёлтый/синий → ученик, остальные → лид.

## Как загрузить свои таблицы (CSV)

Программа читает CSV. Excel, Google Sheets и Numbers умеют сохранять в этот формат,
так что переносить данные вручную не нужно.

### Шаг 1. Убедиться, что база запущена

Она уже поднята и подключена. Если после перезагрузки Mac контейнер не стартовал:

```bash
docker compose up -d db
```

### Шаг 2. Выгрузить листы в CSV

* **Google Sheets** → Файл → Скачать → «Формат CSV (.csv)»
* **Excel** → Файл → Сохранить как → «CSV UTF-8 (разделитель — запятая)»
* **Numbers** → Файл → Экспортировать в → CSV

Один лист = один файл. Первая строка файла — названия колонок.

### Шаг 3. Положить файлы в `data/import/`

Нужны только те файлы, которые у вас есть, — остальные можно не создавать.
В папке уже лежат образцы с правильными заголовками: откройте их, замените строки
своими данными или просто переименуйте свои файлы.

| Файл | Что в нём |
|---|---|
| `students.csv` | ученики |
| `groups.csv` | группы (необязательно — создадутся из колонки «Группа» у учеников) |
| `payments.csv` | оплаты |
| `leads.csv` | лиды |
| `expenses.csv` | расходы |

### Шаг 4. Колонки

Названия колонок распознаются на русском, узбекском и английском — переименовывать
ничего не нужно. Лишние колонки просто игнорируются.

**students.csv** — обязательна только первая колонка:

| Колонка | Понимает также | Пример |
|---|---|---|
| ФИО | `ism`, `o'quvchi`, `name` | Aziz Karimov |
| Телефон | `telefon`, `raqam`, `tel` | +998901234567 |
| Группа | `guruh`, `group` | Ingliz-01 |
| Курс | `kurs`, `yo'nalish`, `fan` | Ingliz tili |
| Цена | `narx`, `oylik to'lov` | 450 000 |
| Статус | `holat` | `faol` / `muzlatilgan` / `ketgan` |
| Дата начала | `boshlagan sana`, `sana` | 15.03.2026 |
| Долг | `qarz`, `qarzdorlik` | 400 000 |
| Дата долга | `qarz sanasi` | 05.08.2026 |
| Источник | `manba`, `qayerdan` | Instagram |
| Админ | `mas'ul` | Администратор 1 |
| Уроков | `dars soni` | 12 |

**payments.csv:** ФИО · Сумма · Способ (`naqd` / `karta` / `перевод`) ·
Дата · Принял · Первый платёж (`ha` / `да` / `+`)

Слово `terminal` в колонке способа тоже понимается — оно превращается
в «Карту»: оплата через POS-терминал и есть оплата картой.

**leads.csv:** ФИО · Телефон · Источник · Статус · Качественный (`sifatli`) · Оператор · Дата

**expenses.csv:** Статья · Название · Сумма · Дата · Способ · Автор

**groups.csv:** Группа · Курс · Преподаватель · Цена · Вместимость

Форматы значений система приводит сама: `450 000`, `1,200,000`, `$300` — всё это суммы;
`14.08.2026`, `2026-08-14`, `14/08/26` — всё это даты.

### Шаг 5. Проверить и загрузить

```bash
npm run db:import -- --dry-run    # показывает, что распозналось; в базу не пишет
npm run db:import                 # загружает
```

`--dry-run` печатает первые строки каждого файла и список колонок, которые он увидел.
Если в имени или сумме пусто — строка попадёт в раздел «Не загружено» с причиной.

Повторная загрузка добавляет данные к существующим. Чтобы залить заново с нуля:

```bash
npm run db:import -- --replace    # удаляет прежних учеников/платежи/расходы, учётки остаются
```

### Что происходит с долгом

Долг из вашей таблицы превращается в просроченный счёт (`Invoice` со статусом `OVERDUE`),
а не в отдельную цифру. Поэтому ученик сразу появляется в «Должниках» с датой
образования долга, а сумма сходится с кассой в разделе «Финансы».

### Замороженные ученики

Колонка «Статус» со значением `muzlatilgan` / `заморожен` — этого достаточно.
Если такой колонки нет, все ученики загрузятся как активные; когда данные о
заморозках появятся, добавьте колонку и повторите импорт с `--replace`.

## Что на дашбордах

**Обзор (Shtab).** Чистая прибыль как ведущее число, приход за 14 дней, активные ученики,
новые за месяц, конверсия лид → ученик, касса дня по способам оплаты, распределение
учеников по направлениям, заполненность групп, заморозки, отток, должники, лента журнала.

**Администратор.** Новые клиенты за сегодня и откуда пришли, оплаты, визиты,
воронка удержания (1-й → 2-й → 3-й урок), таблица должников со сроком просрочки
и датой образования долга, списки замороженных и ушедших.

**Call-центр.** Звонки за сегодня и за 14 дней, Call dars, лиды и качественные лиды,
визиты в офис, продажи online/offline, источники лидов, таблица по операторам.

**Финансы (Moliya).** Поступления сегодня, касса по способам (Naqd / Kart /
перевод), расходы по статьям, чистая прибыль и маржа, должники, последние платежи
и расходы с указанием автора.

## Три способа оплаты, а не четыре

Наличные (`CASH`), карта (`CARD`) и перевод (`TRANSFER`). Терминала в списке нет:
оплата через POS-терминал — это та же оплата картой, и держать два способа
значило показывать одни и те же деньги в двух местах кассы.

Слово «терминал» из Sahab и из CSV читается как «карта» (`src/server/sync/refresh.ts`,
`scripts/import/csv.ts`). В базе у старых строк ещё стоит `TERMINAL` — значение
осталось в `schema.prisma`, потому что Postgres не даёт удалить его, пока на него
ссылаются строки, а Prisma роняет запрос на незнакомом значении enum. При чтении
такие строки приводятся к `CARD` (`src/server/data/source.ts`), поэтому на экранах
терминал уже не встречается. Полностью старые значения уходят при следующей
синхронизации с Sahab — она переписывает платежи и расходы целиком.

## Любой блок сворачивается

У каждого заголовка на дашбордах и на карточках слева стоит шеврон: клик прячет
содержимое, повторный — возвращает. Сворачивается и группа целиком («Ключевые
показатели», «Касса и структура»), и отдельная карточка внутри неё, и плашки
с итогами в шапке списков.

Что свёрнуто — помнится по каждому сотруднику в cookie `lid_collapsed`
(`src/lib/collapsed.ts`) и переживает переход между экранами и перезагрузку.
Cookie, а не localStorage, потому что страницы рисуются на сервере: он читает
её в `src/app/(dashboard)/layout.tsx` и сразу отдаёт нужный вид, поэтому
свёрнутый блок не мелькает при загрузке.

Компоненты — в `src/components/ui/collapsible.tsx`: `CollapsibleGroup` (группа
с заголовком), `CollapsibleCard` (карточка), `CollapsibleStats` (итоги в шапке
списка). У каждого блока свой ключ вида `shtab.kpi`; у списков ключ берётся
из адреса страницы.

## Один филиал — но архитектура на несколько

`branchId` остался во всех таблицах и во всех запросах. Чтобы открыть второй филиал,
нужно поставить `singleBranch: false` в `src/config/app.ts` и вернуть в шапку
переключатель филиалов — данные и схема переделки не потребуют.

## История изменений (AuditLog)

Таблица `audit_logs`: кто (`actorName`, `actorRole`), что (`entity`, `entityId`, `entityLabel`),
какое поле (`field`, `oldValue`, `newValue`, JSON-дифф `changes`), почему (`reason`),
когда, с какого IP. Писать только через `lib/audit.ts` — с `db: tx`, чтобы запись
откатывалась вместе с неудачной операцией.

| Вопрос | Как отвечается |
|---|---|
| Кто перевёл лида в статус «Ученик»? | `entity: "Lead", action: "CONVERT"` → автор и время |
| Когда и почему ученик стал должником? | `entity: "Student", action: "DEBT_OPENED"` + `reason` |
| Кто добавил расход из кассы? | `action: "EXPENSE_CREATE"`, плюс жёсткая связь `Expense.createdById` |

## Долг — не флаг, а данные

`Invoice` (начисление за месяц) минус `PaymentAllocation` (разнесение платежей).
Просроченный счёт → `status: OVERDUE` → ученик в «Qarzdorlar», `Student.debtSince`
фиксирует дату начала долга. Поэтому сумма долга на дашбордах сходится с кассой.

## Дизайн

Палитра прогнана через валидатор доступности: категориальные цвета различимы
при дальтонизме (ΔE ≥ 9.2 в светлой теме, ≥ 9.4 в тёмной), у каждого статуса —
точка-индикатор, а не только цвет. Тёмная тема включается системной настройкой.
Токены — в начале `src/app/globals.css`, менять цвета нужно только там.
